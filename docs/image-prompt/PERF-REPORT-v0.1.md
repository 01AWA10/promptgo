# 图像提示词性能与体积报告 v0.1

> 阶段 4 交付物 · 2026-11-16 · 数据由 `python tools/perf_bench.py` 实测生成（同进程现算，无写死数字）
> 关联：[`IMAGE-PROMPT-SPEC-v1.0.md`](IMAGE-PROMPT-SPEC-v1.0.md) §5 长度预算、[`../IMAGE-PROMPT-ITERATION-PLAN.md`](../IMAGE-PROMPT-ITERATION-PLAN.md) §1.4 兼容性约束

## 1. 结论

| 项 | 门槛 | 实测 | 判定 |
| --- | --- | --- | --- |
| 图像提示词 P95 耗时（500 字） | ≤30 ms | **2.48 ms**（P50 2.10、单轮 max 7.02） | 通过（余量 12 倍） |
| 文本链路 P95（320 字） | 不回退 | **1.94 ms** | 通过 |
| 组件体积 | ≤44 KB | **40,936 B**（gzip 12,403 B），余量 4,120 B | 通过（余量 9.1%） |
| `/v1/meta` 负载 | ≤12 KB | **10,106 B** | 通过 |
| 其中 `image_*` 字段 | ≤5 KB | **3,335 B** | 通过 |

**一句话**：延迟有 12 倍余量，体积只剩 12% 余量——后续该盯的是组件大小，不是性能。

## 2. 测量口径（为什么这些数字可信）

1. **P95 用图像提示词 500 字输入**，不是 320 字文本样例：输入越长，`_image_plan` 的词典扫描与裁剪越贵，用短文本测会得到偏乐观的数。
2. **计时只算 `enhance()` 全程**（`normalize → analyze → render → score`），不含 HTTP 与 SSE 分帧——计划里的 30 ms 是纯引擎预算，混进协议开销会让结论无法归因。
3. **300 次 × 3 轮，取 P50/P95 的轮中位数**，max 取三轮峰值。本机单轮 P95 会随后台进程抖到 4 ms 量级而 P50 稳定在 2.1 ms，单轮取样等于用运气下结论，故多轮取中位并把各轮 P95 留档。
4. **体积取磁盘字节数**（组件）与 `json.dumps(META, ensure_ascii=False)` 的 UTF-8 字节数（元数据）；gzip 仅作参考，静态资源走明文下发。
5. 预算常量与 `tests/test_frontend.py::SIZE_BUDGET`（44 KB）同一口径，避免「报告一套、测试一套」。

## 3. 耗时明细

| 场景 | P50 | P95（三轮中位） | 三轮 P95 | max |
| --- | --- | --- | --- | --- |
| 图像 500 字（generic） | 2.10 ms | **2.48 ms** | 2.48 / 2.48 / 2.51 | 7.02 ms |
| 图像 500 字（MJ 方言） | 2.14 ms | **2.70 ms** | 2.88 / 2.70 / 2.53 | 4.83 ms |
| 文本 320 字（对照） | 1.61 ms | 1.94 ms | 1.94 / 1.93 / 2.52 | 4.03 ms |
| 仅 `analyze()`（500 字） | 2.01 ms | 2.73 ms | 3.76 / 2.39 / 2.73 | 4.86 ms |

> 表中数字取自**一次完整运行**（300 次 × 3 轮）。复跑会有 ±0.3 ms 抖动（同一机器上实测 P95 在
> 2.4–3.1 ms 区间浮动），因此不要把 0.1 ms 级别的差异当结论；门槛判定（30 ms）与 12 倍余量不受影响。

**读法**：

- MJ 方言比 generic 贵约 0.2 ms，差异来自尾部参数拼接与英文负面词转换（`to_en` 逐条查表），不是词典扫描。
- 「仅 `analyze()`」与「`enhance()` 全程」的 P50 只差 0.09 ms，说明**瓶颈在分析层**（`_image_plan` 的七维词典扫描 + 长度裁剪），渲染与评分可忽略。要压延迟就动词典扫描（前缀过滤、词表懒加载），而不是渲染。
- 图像分支比文本链路多约 0.5 ms（2.10 vs 1.61）；绝对值都在 3 ms 内，距离 30 ms 门槛很远，因此**性能不是当前瓶颈**，也不应成为拒绝加词的理由。

## 4. 体积明细

| 对象 | 字节 | gzip | 预算 | 余量 |
| --- | --- | --- | --- | --- |
| `web/prompt-enhancer.js` | 40,936 | 12,403 | 45,056（44 KB） | 4,120（9.1%） |
| `/v1/meta` 整体 | 10,106 | — | 12,288（12 KB） | 2,182 |
| └ `image_*` 八组 | 3,335 | — | 5,120（5 KB） | 1,785 |

**关键决策回顾**：324 条全量词表不进 `/v1/meta`（中文 + 英文两列约 8.7 KB，会直接击穿 5 KB 字段预算），只下发 `id + 中文标签`，别名与场景权重留在服务端；`image_*` 因此稳定在 3.3 KB。详见 [`IMAGE-META-v0.1.md`](IMAGE-META-v0.1.md)。

**风险**：组件余量只剩 5.2 KB，而阶段 5 还要加「风格/构图/比例 chips + 平台切换」。按现有 chip 实现（复用 `_renderChips`、单行 CSS）估算新增 1.5–2 KB 仍可容纳；若同时加平台下拉与筛选面板会逼近上限，届时需先压缩，或让 chips 按 `/v1/meta` 分组懒加载换空间。

## 6. 复现命令

```bash
python tools/perf_bench.py           # 本报告的全部数字
python tools/perf_bench.py --json    # 机器可读
python tools/image_eval.py           # 120 条断言与长度区间
```

`perf_bench.py` 的 `gates` 字段把四条门槛算成布尔值，未达标时退出码 1，可直接挂进 CI 做性能与体积回归。

## 7. 残留风险

1. **单机测量**：只在开发机（Windows / CPython 3.14）跑过，未做跨机对比；不同机器的绝对值会有偏差，但 12 倍余量足以吸收。
2. **未覆盖并发**：HTTP 线程池与限流不在本报告口径内（只测纯引擎），真实并发下的 P95 需另用压测工具。
3. **体积只测组件单文件**：演示页与其他静态资源未纳入预算；若后续加图像预览能力需重新核算。
4. **`image_*` 随词表增长**：当前按 `[:16]` 等上限截断下发，词表扩容不会线性抬高体积，但被截断的词用户看不到——扩词时需复核「展示哪些」而不是「全量下发」。
